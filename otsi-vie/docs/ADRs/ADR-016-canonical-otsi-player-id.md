# ADR-016: One permanent canonical OTSI Player ID per registered player

Status: accepted (owner directive, 2026-10-26)

## Context
The owner requires exactly one unique, permanent, immutable public identity per registered football player, `OTSI-CCC-YYYY-NNNNNN` (20 characters), used identically by the registry, rosters, matches, video analysis, tracking, overlays, events, tactics, metrics, Reel Builder, Clip Studio, spotlight rendering, reports, search, share links, export manifests and audit. The reference schema (0001) had `players.canonical_otsi_id varchar(32)` with a case-INSENSITIVE collation, no format check, no allocator, no immutability and no lifecycle beyond PENDING/VERIFIED/RETIRED (audit findings G1–G8 in `blueprint/CHANGELOG.md`). The older blueprint text said allocation stays with the old website allocator; the owner's directive supersedes it for the greenfield application (a future website integration links IDs through `player_external_ids`, it never mints them).

## Decision
1. **Format and storage.** `VARCHAR(20) CHARACTER SET ascii COLLATE ascii_bin`, `CHECK REGEXP_LIKE(id, '^OTSI-[A-Z]{3}-[0-9]{4}-[0-9]{6}$', 'c')`, `UNIQUE`. (Finding: on MySQL 8.4.13 the same CHECK on a `CHAR(20)` column rejects valid IDs; `VARCHAR(20)` behaves correctly, the pattern fixes the length.)
2. **Allocation scope.** The namespace is (country code at issuance, UTC issuance year). `canonical_id_sequences` holds one counter per namespace; the ID prefix makes namespaces disjoint, so the full ID is globally unique (also enforced by `UNIQUE` on the ID and on (country, year, sequence)). Country = ISO 3166-1 alpha-3 + ENG/SCO/WAL/NIR (`countries`, 0006). Year = the server's UTC year, never the caller's.
3. **The allocator** `sp_issue_canonical_player_id` (0007) is the only way an ID is issued: one transaction; locks the player row; reserves the number with ONE atomic upsert that takes the counter row's exclusive lock (measured: lock-then-insert deadlocked under 40 concurrent requests); refuses an exhausted namespace (past 999999, never wraps); writes the append-only issuance ledger, registers the player and an audit event. Idempotent: an already-registered player gets its ID back; a repeated `request_key` returns the same ID and cannot mint for another player. The service retries a deadlock (1213) by calling again.
4. **Immutability, defence in depth.** Triggers refuse: an ID on insert, any change of an issued ID, an ID not issued to that player, updating/deleting the ledger, a sequence going anywhere but +1, deleting a registered player, re-provisioning a registered player, undoing a merge. The runtime DB account can only update descriptive player columns (column-level grant) and only EXECUTE the procedures for identity writes.
5. **Lifecycle.** `PROVISIONAL` (imported/unverified; no ID; visible only to the creating organization) → `REGISTERED` (issued exactly once, when an authorised person registers the player through the allocator) → `RETIRED` (ID kept) or `MERGED` (duplicate; ID kept for ever, resolves to the survivor). Player creation is idempotent per (organization, `creation_key`).
6. **Registry, one for all modules.** `players` + `canonical_id_issuances` + `player_merges` + `player_external_ids` + `player_aliases` + `player_nationalities` + `player_club_memberships` + `player_jersey_numbers` + `player_duplicate_candidates`. Transfers, nationality and jersey changes are history rows; they never touch the ID (the country in the ID is an issuance attribute).
7. **Merges.** `sp_merge_players` (survivor must be REGISTERED, reason required, append-only decision, fixed lock order). No historical reference is rewritten; `v_player_identity` resolves any player (through chains A→B→C) to the current survivor and its canonical ID.
8. **Tracking.** detection (observation row) ≠ `track_id` (temporary, per run) ≠ `player_id` (internal) ≠ `canonical_otsi_id` (public) ≠ jersey number. A track becomes a player only through an appended `track_identity_decisions` row; tracks never create players or IDs. Corrections append a superseding decision for the SAME track with a reason (linear history, append-only). A decision can only target a live (not MERGED/RETIRED) player. `v_track_current_identity` gives each track's current decision; a track without one is "Unidentified Player".
9. **Spotlight / reels.** A reel target pins `(identity_decision_id, track_id, player_id)` to the exact decision for that same track and player (composite FK), so a reused or reassigned track cannot carry the spotlight to another person. When the track's current decision is no longer the pinned one, the target is stale and the export gate blocks the render (service + test 18).
10. **API contract.** Every response that identifies a player carries `player_id` (internal) and `canonical_otsi_id` (resolved through `v_player_identity`, `null` for PROVISIONAL, and never shown as confirmed unless REGISTERED); unresolved tracks carry no player.

## Evidence
`tests/db/test_identity.py` (owner tests 1–14, 16–18 at database level) and `tests/db/test_behaviour.py`; all on a fresh scratch database. Owner tests 15, 19, 20 (cross-tenant identity operations, reports, all APIs/UI returning the same ID) need the API and are tracked in `docs/IMPLEMENTATION_STATUS.md`.

## Alternatives rejected
A single global counter (contention, and the owner's format carries country and year); application-generated IDs (no database guarantee under concurrency); deriving IDs from jersey numbers or track numbers (explicitly forbidden); rewriting historical rows on merge (destroys provenance).
