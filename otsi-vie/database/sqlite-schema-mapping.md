# SQLite schema mapping — MySQL → SQLite

How the 74 MySQL migrations (0001–0075; **0070 does not exist**) became the
SQLite schema for user PCs. Generated by `tools/db/sqlite_translate.py`
from the MySQL files; hand-written only where a generator cannot go
(`tools/db/sqlite_triggers.sql`, the trigger overlay). Regenerate with:

```
cd otsi-vie/tools/db && python3 sqlite_translate.py
```

Last run: **157 tables, 126 indexes, 5 views, 34 triggers, 15 touch
triggers, 69 warnings**. Full per-column report:
`database/sqlite-translation-report.json`; per-column collation decisions:
`database/sqlite-column-collations.csv` (1,494 columns).

## Rules applied to every table

- **STRICT tables.** Only `INTEGER / REAL / TEXT / BLOB / ANY` are allowed,
  so every MySQL type is mapped (verified on SQLite 3.45.1: NUMERIC,
  VARCHAR, BIGINT, CHAR, DATETIME, BOOLEAN and JSON are all rejected in
  STRICT).
- **Dates as INTEGER milliseconds** since the Unix epoch
  (`CAST(unixepoch('subsec')*1000 AS INTEGER)`), never DATETIME or TEXT.
  `DEFAULT CURRENT_TIMESTAMP(6)` becomes
  `DEFAULT (CAST(unixepoch('subsec')*1000 AS INTEGER))`.
- **Booleans as INTEGER 0/1** (`TRUE`/`FALSE` → 1/0).
- **JSON as TEXT with a `json_valid` CHECK** (`ck_json_*`, 74 columns).
  JSON1 functions (`json_object`, `json_extract`, …) are used in defaults
  and checks; `DEFAULT (json_object())` needs the parentheses — bare
  `DEFAULT json_object()` is a SQLite syntax error.
- **Foreign keys declared in DDL and enforced** (`PRAGMA foreign_keys=ON`
  in the runner; `foreign_key_check` passes on the bootstrap: 0 violations).
- **TEXT columns get an explicit collation** (see "Collations" below).

## Type mapping

| MySQL | SQLite | Notes |
|---|---|---|
| CHAR(n) / VARCHAR(n) / TEXT / MEDIUMTEXT / LONGTEXT | TEXT + `CHECK(length(col) <= n)` (865 length checks) | Length is enforced; MySQL's `VARCHAR(255)` truncation-on-insert is not reproduced — overlong values are refused instead |
| ENUM('a','b',…) | TEXT + `CHECK(col IN ('a','b',…))` (31 enum checks) | Enum lists are taken from the final schema state; `assets.kind` grows across migrations 0013/0014/0032/0044/0054/0067/0068 |
| SET | — (error) | No SET column exists in any migration |
| JSON | TEXT + `CHECK(json_valid(col))` | 73 JSON columns |
| DECIMAL(p,s) / NUMERIC(p,s) | REAL | **12 columns** (see "Known divergences"): exact-decimal semantics are lost; all 12 hold scores, ratios, speeds or percentages — money is stored as BIGINT minor units, never DECIMAL |
| TINYINT / SMALLINT / MEDIUMINT / INT / BIGINT | INTEGER | UNSIGNED is dropped (19 warnings); values above 2^63−1 are unrepresentable — none exist in practice |
| FLOAT / DOUBLE | REAL | |
| DATETIME / TIMESTAMP / DATE | INTEGER ms | `DATE` columns become ms at midnight UTC |
| BOOLEAN / BIT(1) | INTEGER 0/1 | |
| BLOB / MEDIUMBLOB / BINARY / VARBINARY | BLOB | 1 MEDIUMBLOB column |
| AUTO_INCREMENT BIGINT UNSIGNED PK | `INTEGER PRIMARY KEY AUTOINCREMENT` | 7 tables: job_events, audit_events, outbox_events, share_link_access, billing_webhook_inbox, security_events, search_documents |

## Expressions and functions

| MySQL | SQLite |
|---|---|
| `REGEXP_LIKE(x, '^...$', 'c')`, `x REGEXP 'pat'` | GLOB (`{n}` / `{n,m}` expanded to an OR of patterns). All 7 regex patterns inventoried: `^#[0-9A-F]{6}$`, `^[0-9]{1,2}$`, `^[a-z][a-z0-9_]*([.][a-z][a-z0-9_]*)+$` (audit action names), `^OTSI-[A-Z]{3}-[0-9]{4}-[0-9]{6}$`, `^[A-Z]{3}$`, `^[a-z][a-z0-9_.-]*$`. Two patterns get bespoke exact GLOB+NOT GLOB equivalents (see translator `_glob_condition`) |
| `JSON_TYPE(x)` | `json_type(x)` with `'OBJECT'`→`'object'`, `'ARRAY'`→`'array'` |
| `JSON_OBJECT / JSON_ARRAY / JSON_EXTRACT / JSON_VALID` | `json_object / json_array / json_extract / json_valid` |
| `JSON_UNQUOTE(JSON_EXTRACT(...))` | `json_extract(...)` (already returns text) |
| `IF(a,b,c)` | `CASE WHEN a THEN b ELSE c END` |
| `LPAD(x,n,'0')` | `printf('%0nd', x)` |
| `CHAR_LENGTH(x)` | `length(x)` |
| `OCTET_LENGTH(x)` | `length(CAST(x AS BLOB))` |
| `CONCAT(a,b)` | `a \|\| b` |
| `<=>` | `IS` |
| `CAST(x AS CHAR)` / `AS BINARY` / `AS SIGNED` | `CAST(x AS TEXT)` / `AS BLOB` / `AS INTEGER` |
| `UUID()` | `lower(hex(randomblob(4))||'-'||…)` expression |
| `UTC_TIMESTAMP()` / `YEAR(UTC_TIMESTAMP())` | ms-now / `CAST(strftime('%Y','now') AS INTEGER)` |
| `TRUE` / `FALSE` | `1` / `0` |
| Generated column `open_email` (0036, `IF(...)`) | Stored column + `CASE WHEN` expression |

## Collations (per column)

- TEXT default: **`COLLATE NOCASE`** (990 columns) — approximates MySQL
  `utf8mb4_0900_ai_ci` case-insensitivity for ASCII. **Accent folding is
  NOT reproduced** (stock SQLite has no ICU): `café` ≠ `cafe` on SQLite.
  Recorded as a known gap; no app query is known to depend on accent
  folding.
- **BINARY** (8 columns, identifiers/codes/hashes where case matters):
  `players.canonical_otsi_id`, `countries.code`,
  `canonical_id_sequences.country_code`,
  `canonical_id_issuances.canonical_otsi_id`,
  `canonical_id_issuances.country_code`,
  `player_nationalities.country_code`, `search_terms.term`,
  `player_profile_details.international_country_code`.
  The rule: BINARY iff an explicit `ascii_bin` / `utf8mb4_bin` collation
  or `CHARACTER SET ascii` was declared (11× `ascii_bin`, 1×
  `utf8mb4_bin`, 14× `CHARACTER SET ascii` in MySQL). Everything else is
  NOCASE.
- One subtlety preserved: `0011_credential_email_case.sql` fixes 0010's
  email CHECK to `CAST(email_normalized AS BINARY) = CAST(LOWER(...) AS
  BINARY)` because MySQL's case-insensitive collation made the original
  check pass mixed case. The SQLite translation keeps the CAST AS BLOB
  form, so the check is exact.

## DDL constructs

| MySQL | SQLite | Count |
|---|---|---|
| `CREATE TABLE` | `CREATE TABLE ... STRICT` with mapped types, length/enum/json CHECKs, collations, inline FKs | 157 tables |
| `ALTER TABLE ... ADD CONSTRAINT / ADD FOREIGN KEY` | **Table rebuild** (CREATE new table, INSERT SELECT, DROP old, RENAME) + recreate indexes and triggers; wrapped in `PRAGMA legacy_alter_table=ON` (a rebuild RENAME fails when a view names the table — verified) | 303 rebuild blocks across 41 migrations (0001 alone adds ~180 FKs as deferred ALTERs) |
| `ALTER TABLE ... ADD COLUMN` | Rebuild when the column is NOT NULL without a default; plain `ADD COLUMN` when it has a default or is nullable | 107 ADD COLUMN |
| `ALTER TABLE ... DROP CHECK / DROP INDEX / DROP FOREIGN KEY` | Rebuild (SQLite cannot drop a constraint) | 18 DROP CHECK, 2 DROP INDEX, 1 DROP FOREIGN KEY |
| `ALTER TABLE ... MODIFY COLUMN` | Rebuild | 12 |
| `ALTER TABLE ... ADD UNIQUE / ADD KEY / ADD INDEX` | `CREATE UNIQUE INDEX` / `CREATE INDEX` | 9 / 8 / 2 |
| `CREATE INDEX` / `DROP INDEX` | `CREATE INDEX` / `DROP INDEX` | 43 / 2 (126 indexes total in final schema) |
| `ALTER TABLE ... AFTER col` / `FIRST` | **Dropped** — column order is not preserved (38 warnings). Column order is not part of any contract; `SELECT *` order differs from MySQL |
| `ON UPDATE CURRENT_TIMESTAMP` | AFTER UPDATE touch trigger (below) | 15 columns |
| `CREATE VIEW` | `CREATE VIEW` (same SQL, MySQL functions translated) | 5: `v_player_identity`, `v_track_current_identity`, `v_track_link_current`, `v_run_team_current`, `v_track_jersey_current` |
| Standalone `INSERT` / `UPDATE` / `DELETE` | Translated DML (`UPDATE t alias` → `UPDATE t AS alias`, alias stripped from SET left-hand sides) | 7 INSERTs, 3 UPDATEs (incl. 0006 countries seed, 253 rows; 0039 INSERT…SELECT with UUID()); no standalone DELETE |
| `CREATE PROCEDURE` | **Application code** (below) | 2 |
| `CREATE FUNCTION` / `CREATE EVENT` | — (none exist) | 0 |

## Triggers — every one, and what it became

34 MySQL triggers → **34 SQLite triggers, same names**. `SIGNAL` becomes
`SELECT RAISE(ABORT, '<exact message>')` — the messages are contractual
(the API maps them in `apps/api/src/core/problem.ts`), so they are kept
character-for-character.

**Critical rule discovered empirically:** SQLite fires same-table triggers
alphabetically, NOT in creation order. A MySQL trigger with several
SIGNALs is therefore **one** SQLite trigger holding one
`SELECT RAISE(ABORT,'msg') WHERE <cond>;` per check in MySQL order
(a SELECT whose WHERE is false produces no rows, so its RAISE never
fires — verified). The hand-written overlay is
`tools/db/sqlite_triggers.sql`, sections `-- == NNNN ==`.

| Source | SQLite trigger(s) | Decision |
|---|---|---|
| 0002 `trg_projects_update`, `trg_reels_update` | Same names (AFTER UPDATE touch + `version = OLD.version+1`) | Trigger |
| 0002 `trg_render_transition` | Same name (BEFORE UPDATE) | Trigger — render state machine has **no API-side enforcement**; only this trigger enforces it |
| 0005 / 0014 / 0016 append-only history | `trg_*_no_update`, `trg_*_no_delete` on audit_events, event_decisions, identity_decisions, identity_review, jersey_decisions, link_decisions, merges, roster_changes, team_assign, sequences, issuances | Trigger |
| 0005 / 0014 / 0016 reason guards | `trg_jersey_decisions_reason`, `trg_link_decisions_reason`, `trg_team_assign_reason`, `trg_tid_target_is_live` | Trigger |
| 0005 / 0014 / 0016 players guards | `trg_players_insert_guard`, `trg_players_update_guard`, `trg_players_delete_guard` | Trigger (canonical-ID immutability, allocator-only issue, merge-final) |
| 0071 wallet immutability | `trg_wallet_ledger_no_delete`, `trg_wallet_ledger_no_update` | Trigger — refuses everyone, retention included, exactly as MySQL |
| 0071 sequences | `trg_sequences_no_delete`, `trg_sequences_only_advance` | Trigger |

**Retention DELETE exception — the one behaviour SQLite cannot copy:**
the 0005/0014/0016 DELETE triggers refuse every delete on SQLite, because
MySQL's exception (allow the retention account, identified by `USER()`)
has no SQLite equivalent. On MySQL, retention deletes are allowed; on
SQLite they are refused at the trigger and must go through the API
adapter's retention bypass instead. Owner: `RetentionService.eraseSubject()`
/ `purgeTrash()` in `apps/api/src/modules/retention/retention.ts` (agent A
owns the bypass; the trigger behaviour is tested in
`tools/db/test_sqlite_migration.py`). The wallet ledger is unaffected —
it refuses everyone in MySQL too, so SQLite matches exactly.

## Touch triggers (ON UPDATE CURRENT_TIMESTAMP)

15 columns become 15 AFTER UPDATE triggers named
`trg_<table>_<column>_touch`:
`ai_analyst_assessments`, `ball_marks`, `bank_accounts`,
`bank_transfer_orders`, `effect_presets`, `library_folders`,
`match_periods`, `org_retention_policies`, `org_templates`,
`player_assessments`, `player_profile_details`, `players`,
`user_page_modes`, `video_sources`, `wallet_pack_requests`
(all `updated_at`). `projects` and `reel_projects` also bump `version`
(their triggers live in the 0002 overlay, above).

Each trigger fires `WHEN NEW.updated_at = OLD.updated_at` and stamps
`MAX(now_ms, OLD.updated_at+1)` — so the recursive firing sees a changed
value and stops after exactly one extra write (verified). **Documented
divergence:** a user UPDATE that sets `updated_at` explicitly gets no
version bump on SQLite; the app never sets `updated_at` itself (it relies
on the trigger), so this is a divergence, not a behaviour the app depends on.

## Procedures — moved to application code

SQLite has no stored procedures. Both procedures keep their exact checks
and error messages, inside one transaction, in the adapter (agent A owns
the implementation; the tests named here are API-suite tests, not mine).

| Procedure | Now enforced by | Notes |
|---|---|---|
| `sp_issue_canonical_player_id` (0018 version supersedes 0007; non-locking lookup) | `PlayersService.register()` calls the adapter's `issueCanonicalPlayerId()` | Same checks/messages (CANONICAL_ID_IMMUTABLE, CANONICAL_ID_ONLY_BY_ALLOCATOR, CANONICAL_SEQUENCE_EXHAUSTED); sequence reserved with `INSERT … ON CONFLICT DO UPDATE` + re-read |
| `sp_merge_players` | `PlayersService.merge()` calls the adapter's `mergePlayers()` | Same checks/messages (MERGE_REASON_REQUIRED, MERGE_NEEDS_A_RECORDED_DECISION, MERGE_IS_FINAL, IDENTITY_DECISION_TARGET_NOT_LIVE); both rows locked in id order |

My tests (migration/backup area) cover the *trigger* side of these
guards (canonical guards, identity-decision reason, merge-final) in
`tools/db/test_sqlite_migration.py`; the procedure-equivalent behaviour
is the API agent's test to write against the adapter.

## Known divergences (all recorded, none hidden)

1. **DECIMAL → REAL** (12 columns: `camera_transforms.reprojection_error_px`,
   `movement_segments.confidence`, `music_beat_grids.periodicity`,
   `music_beat_grids.tempo_bpm`, `pipeline_steps.progress`,
   `player_profile_details.weight_kg`, `possession_episodes.confidence`,
   `reel_clips.playback_speed`, `tactical_windows.coverage_ratio`,
   `worker_jobs.progress`, `worker_status.cpu_percent`,
   `worker_status.gpu_percent`). All hold scores/ratios/speeds/percentages;
   money is BIGINT minor units. Rounding at the last decimal is possible.
2. **UNSIGNED dropped** (19 columns). Values above 2^63−1 unrepresentable.
3. **Column order lost** (38 `AFTER`/`FIRST` clauses dropped).
4. **No accent folding** (NOCASE is ASCII-only).
5. **Retention DELETE exception** (above) — needs the adapter bypass.
6. **Touch-trigger version bump** skipped when `updated_at` is set
   explicitly (above).
7. **Length enforcement is refusal, not truncation** (above).

## Verification (this VM)

- Translator `--check`: 157 tables, 126 indexes, 5 views, 34 triggers,
  15 touch triggers, 69 warnings.
- Bootstrap creates **158 tables** (157 + `schema_migrations`), 126
  indexes, 5 views, 49 triggers (34 + 15 touch), all STRICT,
  `integrity_check` ok, zero FK violations, 253 countries rows, 74
  `schema_migrations` rows.
- **Incremental application of all 74 per-migration files produces a
  schema identical to the bootstrap** (table/column/index/view/trigger
  sets and normalized DDL equal).
- `python3 test_sqlite_migration.py` — **16 tests, all pass** (4.4s):
  bootstrap completeness, incremental≡bootstrap, noop up, bootstrap
  refusal, splitter, backup manifest, failing-migration restore
  byte-identical, append-only, wallet immutability, render state machine,
  canonical guards, identity-decision reason, touch trigger,
  JSON/ENUM/length/FK checks, collation decisions, translator report counts.
- `node --check backend.js` passes; `dbBackend()` defaults to `sqlite`,
  `sqliteDbPath('D:\\OTSI-VIE')` → `D:\OTSI-VIE\db\otsi-vie.sqlite`,
  invalid backend values are rejected.
- `db_setup.py` SQLite mode: fresh run creates the file from the
  bootstrap; repeat run reports 74 migrations applied; `migrate.py`
  CLI `status` / `up` / `bootstrap` work; a second `bootstrap` over an
  existing database refuses (exit 2).
- SQLite trigger ordering, `SELECT RAISE … WHERE false`, touch-trigger
  recursion, `legacy_alter_table=ON` rebuilds, and `UPDATE t AS alias`
  were each verified empirically during development.
