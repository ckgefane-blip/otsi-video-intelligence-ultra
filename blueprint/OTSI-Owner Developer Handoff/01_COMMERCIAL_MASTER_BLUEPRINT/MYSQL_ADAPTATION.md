# MySQL 8.4 LTS — canonical database decision

**Deployment target:** a NEW isolated database `otsi_owner_vie` on a MySQL 8.4 LTS server; phpMyAdmin is the administrative UI. Do not overwrite `sfbhenfezi_vie` or any existing database. The screenshot confirms host localhost:3306 but not the server engine/version; verify `SELECT VERSION()` and MySQL vs MariaDB before running migrations. MariaDB is **not** presumed compatible with MySQL 8.4.

**Execution source:** `mysql_migrations/001_full_schema_mysql84.sql` then `002_guard_triggers_mysql84.sql`. The incompatible legacy SQL is excluded from this handoff. Only the MySQL migrations are available for implementation.

**Critical:** This is a MySQL-translated *reference DDL*, not a tested/production-certified schema. Before executing, developers MUST lint against actual MySQL 8.4 in disposable containers and resolve all reported failures, dependency/type/index issues. Then generate small repeatable versioned migrations (not one giant manual production import), unit and integration test tenant scope, billing and rights policies and perform rollback rehearsal. The generated DDL also needs review for missing constraints and date/time semantics.

**Model conventions:** UUIDv7 IDs are generated by API/worker and stored as CHAR(36); timestamps DATETIME(6) UTC; JSON uses MySQL JSON; categorical value sets ENUM or bounded VARCHAR with CHECK; automatic increment BIGINT UNSIGNED; full-text search is separate Meilisearch/OpenSearch or MySQL FULLTEXT based on measured needs; geometry/computer vision uses array artifact storage backed by metadata, no SQL extensions. Do not use PG sequence/ARRAY/JSONB/RLS/partial indexes/PLpgSQL/partition-of syntax.

**Tenancy:** Since MySQL has no PostgreSQL native RLS, all organization-scoped access MUST be enforced by authenticated application services through explicit `organization_id` predicates and membership checks. ORM middleware alone is not enough: use service authorization, composite owner checks, negative cross-tenant integration tests, scoped object-storage keys, request audit and least privilege DB roles. Never let browser access MySQL directly.

**Tracking scale:** `track_observations` reference table is unpartitioned. High-volume traces should be written as compressed columnar segment artifacts in S3 and materialized, queryable observation windows in MySQL. Only partition when compatible with foreign keys and tested; MySQL partitioned InnoDB tables have foreign-key restrictions. 

**Roles:** A migration account can change schema, a runtime app account has only least-required DML, a read-only analyst account has restricted access, and database credentials live in a secrets manager. phpMyAdmin must not be publicly exposed.

**Payment:** provider webhook signature verification, deduplication and transactional outbox; no credit card PAN stored in MySQL. Source file and share rights decisions must be checked independently of subscriptions.

**Data safety:** Store original source footage, derived proxies, models, encoded reels and thumbnails in S3-compatible object storage; MySQL stores metadata, checksums, rights and audit events. Require encryption, backups, point-in-time recovery and restore drills.

**Release blocking:** no claim of commercial production readiness until migration execution, schema drift checks, workload/load benchmarks, rights enforcement, security testing, GPU pipeline correctness and real MP4 output tests pass.
