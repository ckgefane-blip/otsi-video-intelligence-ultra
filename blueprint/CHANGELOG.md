## 2026-10-29 — Page 02: ingest switches saved with the video; the server starts "Send to Analysis" (migration 0020)
- **What changed:** new table `video_ingest_options` (one row per video, from the owner's blueprint `004_media_ingest_rights.sql`, adapted to this schema: composite tenant FK, MySQL types, no ID36/TS6 macros). `POST /v1/uploads` and `POST /v1/imports` accept `options`; `GET /v1/videos` returns them as `ingest_options`. New outbox subscriber `jobs.auto_analysis` (`video.ingested` → one analysis run, decided once per video, recorded on the options row); `analysis/run.ts` is the one run-creation function used by both the Start button and the subscriber.
- **Why:** the 14 switches were only browser preferences, and "Send to Analysis" ran in the browser (it needed the tab open and ignored link imports).
- **Deviation from the blueprint:** the blueprint stores all 14 switches as chosen. Here ten are choices (stabilize and send-to-analysis are carried out; eight are saved as REQUESTS for steps the engine cannot perform yet and are reported back as `not_performed`), and four (players and teams, ball tracking, jersey numbers, metadata) are always written as done by the server because every analysis does them. The 0020 file header describes an earlier version of this rule (twelve server-written columns); the behaviour above supersedes it, with no schema change.
- **Not changed:** existing videos have no options row and are never auto-analysed. The blueprint's `locked_at` (options immutable after the first run) is not implemented: the row is written once and never updated except by the subscriber.
- **Tests:** `apps/api/test/ingestOptions.api.test.ts`; schema inventory regenerated (only the new table added).

## 2026-10-29 (later) — Page 02: per-tab surfaces, removing and cancelling uploads, live progress, separate worker processes (migration 0021)
- **Per-tab surfaces (owner direction):** Upload File = drop zone + Browse File (one video); YouTube / URL = link field + Add URL only; Batch Upload = several files + a queue with each file's own status. Deviation from the reference HTML, which draws file area and link field together on one surface. The eight format cards are informational (no click), as in the reference.
- **Remove / cancel an upload:** `DELETE /v1/videos/:id` (migration 0021 adds `removed_at`, `removed_by`; nothing is deleted, removed videos leave every list and count). Allowed for unverified videos, and for a verified one only while it has no finished analysis and no reel (queued/running analyses are cancelled). Refused with a reason while the video is being checked. Audited as `video.removed`. Visible **Cancel** / **Remove** button on each unfinished row, **Cancel analysis** in the pipeline panel.
- **Live progress:** every upload row carries a progress bar (upload, check, playback copy, analysis) and the pipeline panel an overall analysis bar with the worker's own message; `Video.analysis` (latest run + worker progress) added to the API; the page refreshes every 2 s while anything is moving. A job that has not started reads "Waiting for the worker", never "0%".
- **Worker processes:** the local stack now starts three Python workers (ingest + assessment, playback copy + render, analysis) via `OTSI_VIE_WORKER_KINDS`, so a 70-minute analysis cannot hold up the check of a new upload. Without the variable a worker still handles every kind.
- **Switches:** ten switch values are saved with each upload (the eight for steps the engine cannot perform are saved as requests and reported `not_performed`); see the 2026-10-29 entry above.

Checked by eye on all 2,878 stored thumbnails; the owner assigns the clubs. Page 04 boxes: green / red / yellow.

The earlier run is untouched. Button: Page 04, AI Tools tab.
